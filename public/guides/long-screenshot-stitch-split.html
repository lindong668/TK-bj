Long Screenshots: Stitch and Split Without Breaking the Pixels

A long screenshot is rarely one clean image. It is three or four captures with a strip of repeated content where they overlap, taken at whatever width the window happened to have. Merging them looks like a paste job and is actually a layout computation: the tool has to decide a canvas size, a position for every input, and what to put in the space nobody covers.

This guide works through the rules our Stitch Images and Split Image tools use. Both are deliberately literal — they do exactly what the arithmetic says, including the parts that surprise people. Knowing those parts in advance is the difference between a clean result and a collage that looks almost right.

The one rule that explains everything

Stitching never resizes an input. Each image is drawn at its native pixel dimensions. There is no "make all images the same width" step, no automatic crop and no smart matching. The canvas is sized to hold the largest dimensions, and every image is placed at full size inside it.

That single rule produces every visible artefact. Two screenshots at 1920 and 1280 pixels wide merge into a canvas 1920 pixels wide; the narrow one occupies 1280 and leaves 640 pixels of background beside it. Two screenshots whose content widths differ by 12 pixels — because a scrollbar appeared in one of them — produce a visible 12-pixel step at the seam, even though the images look identical at a glance.

The practical consequence is that preparation matters more than settings. Crop both captures to the same content width before stitching, and the seam disappears. Try to fix it afterwards with alignment and you will only choose which side of the step looks wrong.

What each direction actually computes

The tool offers three layouts, and each has its own canvas formula. Let g be the gap in pixels and n the number of images.

Vertical

  • Canvas width = the widest image; canvas height = the sum of all heights plus g × (n − 1).
  • Each image keeps its own height, so a tall capture followed by a short one simply stacks.
  • Horizontal position follows the alignment control: left, centre or right within the widest column.

Horizontal

  • Canvas width = sum of all widths plus gaps; canvas height = the tallest image.
  • Vertical alignment decides whether each image sits at the top, the centre or the bottom of that height.
  • Useful for before/after pairs, not for page captures.

Grid

  • Cell size = the widest image × the tallest image. Every cell is that size, so unequal images are padded rather than scaled.
  • Columns are adjustable from 2 to 6; rows follow from ceil(n / columns).
  • With nine screenshots and three columns you get a 3 × 3 sheet. With seven, the last row has one cell filled and two blank.

In every mode the background colour fills the gaps and any unused area. White is the default and is the right choice for documents and light interfaces; a mid-grey background makes padded cells obvious, which is useful while you are checking a layout before exporting.

Device pixel ratio: the silent cause of misalignment

Modern screens report a device pixel ratio (DPR). A 1440-pixel-wide browser window on a 2× display produces a screenshot 2880 pixels wide. The same window on a 1× monitor produces 1440. If you capture half a page on a laptop and half on an external monitor, the two files differ by a factor of two, and because stitching does not resize, no alignment setting can reconcile them.

The third row is the one people send to support desks. The fix is not in the stitching tool; it is to recapture both halves under the same conditions: same window width, same zoom level, same monitor. If recapturing is impossible, resize the odd image so both have the same width before stitching, and accept one resampling step. Our Resize Image tool does that without touching the other file.

Overlap, borders and the gap setting

The overlap between two scroll captures is not detected. If capture A ends with a navigation bar and capture B starts with the same navigation bar, the stitched image contains it twice. There is no "remove duplicate rows" option, and adding one would be guesswork: two identical strips can also be legitimate repeated content.

Three settings interact at the seam:

  • Gap (0–60 px, default 8) inserts background between images. Set it to 0 when you want a seamless join; the default 8 is better for a grid where separation is desirable.
  • Background colour shows through the gap and through padded cells. It has no effect on the images themselves.
  • Alignment decides where a narrower image sits inside the widest column. Centre hides asymmetry best; left is correct when the content is anchored to the left edge, which is usually true for web pages.
Overlap is cheaper to remove before stitching: capture the second screenshot starting a little below the last visible line of the first, or crop the duplicated strip with the Crop tool. Ten seconds of cropping saves a seam that cannot be repaired later without editing pixels.

Splitting, and the rounding trap

Splitting cuts a tall image into horizontal strips, all the full original width. There are two modes, and they do not behave the way the labels suggest.

Split evenly takes a count from 2 to 20 and divides the height by it. The slice height is ceil(height / count). For a 3000-pixel image and a count of 3, each slice is exactly 1000 pixels. For 3001 pixels and a count of 3, each slice is 1001 and the last slice is 998 — the tool does not pad the final strip.

By fixed height is the mode that catches people out. The count is derived first: n = ceil(height / sliceHeight). Then the slice height is recalculated as ceil(height / n). The strips you get are therefore at least as tall as you asked, often taller.

If a platform enforces a maximum strip height — many chat apps and CMS uploaders do — the safe approach is to choose a count rather than a height, and verify the resulting slice height before uploading. The tool reports the output count and shows every slice in the results grid, so the check is one glance rather than arithmetic under time pressure.

Splitting only cuts horizontally. There is no vertical split, and no split into a fixed number of columns. For a long screenshot of a wide table, split vertically into strips and then split each strip again only if the platform needs it; the second pass is just another horizontal cut of a narrower file.

The height limit nobody warns you about

Browsers cap the dimensions of an in-memory canvas. The exact limit varies by engine and by available memory, but canvases beyond roughly 16,000 pixels on one side routinely fail or return blank output, and the failure is not always graceful. Stitching ten full-page captures into a 25,000-pixel column can therefore produce an empty result with no useful error message.

The workaround is to stay below the limit by splitting first. Stitch in two halves, keep each under about 12,000 pixels, and deliver them as two files — or downscale the final column to a height the canvas can hold. Downscaling after stitching also reduces file size dramatically, which matters when the destination is a chat app with a 10 MB attachment limit.

A workflow that survives real pages

  1. Capture consistently. Same window width, same zoom, same monitor. Note the DPR if you will mix devices.
  2. Crop each capture to the content width. Remove the scrollbar and any browser chrome. This kills the most common seam problem before it exists.
  3. Remove overlap. Crop the repeated strip from the start of the second capture.
  4. Stitch with gap 0 for a seamless page, or 8 for a grid that should read as separate panels.
  5. Split before sharing if the result is taller than about 12,000 pixels, or if the destination enforces a height limit.
  6. Compress to the target size last, using the KB-target method rather than a quality slider guess.

Steps 2 and 3 are the ones people skip, and they are the only steps that prevent seams rather than disguise them. Everything after that is arithmetic the tools already do for you.

Where the seam shows, and how to hide it

A vertical stitch of two captures taken a few seconds apart rarely joins invisibly, even when the widths match exactly. Three things give it away. The background colour can shift by a level or two when the page repaints, which shows as a faint horizontal band. A JPEG source carries 8×8 block artefacts that do not line up across the join. And if the captures overlap, the duplicated band appears twice, which reads as a stutter in the text.

The fixes are procedural rather than technical. Capture with the same window width and the same zoom, so nothing is resampled. Use a lossless source where possible — a PNG capture stitched and saved as PNG has no second generation of artefacts. And if the two captures overlap, crop the overlap off one before merging; the stitch tool has no overlap detection and will paste both copies. When a visible gap is unavoidable, set the gap deliberately, to 8 or 12 px, on a background that matches the page. A deliberate band reads as a divider; a one-pixel misalignment reads as a mistake.

Planning the height budget before you split

Slice counts are easy to get wrong because the arithmetic is done on the total height, not on the visible content. A 1080 × 5000 capture split into four equal parts gives four slices of 1250 px, because 5000 divides exactly. Split the same file by a fixed height of 1500 and you get 1500, 1500, 1500 and 500 — three full slices and a short tail, which is usually what a chat window wants, since it displays images at a fixed maximum height and a short final image looks intentional.

Work backwards from the destination. If the receiving window shows 1200 px before scrolling, split at 1100 so each slice is fully visible. If the destination imposes a byte limit instead, split at a height that keeps each PNG under it, then compress the slices rather than splitting again. And remember that the browser throttles consecutive downloads: a twenty-slice split is twenty prompts in some browsers, and the 350 ms spacing exists to reduce the chance of the batch being dropped partway through.

Checking the slices before sending

The failure that matters is a cut through a line of text, and it is invisible in a thumbnail. Open the boundary between the first two slices at full size and look for a half-height line of glyphs. If a cut lands badly, change the count by one rather than nudging the height: the boundaries move by a large step and usually clear the text entirely. For a set that will be read on a phone, check the first and last slices specifically — the first carries the header and the last carries whatever was left over, and both are the most likely to be unrepresentative.

Frequently asked questions

Why are my screenshots different widths?Window size, zoom level or device pixel ratio changed between captures. Stitching does not scale, so the difference is preserved. Recapture under identical conditions or resize before stitching.
Can it remove the repeated strip automatically?No. Duplicate detection is ambiguous by nature; crop the overlap manually before stitching.
Why did my requested slice height change?Fixed-height mode derives a slice count first, then recalculates the height so the strips are equal. The result is never shorter than requested, but it can be taller.
Does splitting reduce quality?No. Each slice is a direct pixel copy of a region, exported as PNG. Nothing is resampled.
Why did a very tall stitch fail?The canvas exceeded the browser's dimension or memory limit. Split into smaller groups and stitch each one separately.

Part 1 of this series looked at what happens to an icon after a host has chosen it. This part looks at the choice itself. When a page declares <link rel="icon">, also has a /favicon.ico sitting at the root, ships an apple-touch-icon, and lists three sizes in a web manifest, which one appears in the tab? And what changes when you delete exactly one of those files?

That question generates a surprising amount of support mail, because the answer is not "the biggest one" and not "the last one declared". It is a priority order with different rules per host, and it is heavily cached. Below is a reproducible experiment you can run in ten minutes with a local server, plus the decision tree that came out of it.

The setup

We served a single local page over http://localhost:8787 with six candidate files. Using a real origin matters: file:// pages do not exercise the favicon cache the same way, and some hosts refuse to fetch icons from a file URL.


<link rel="icon" type="image/png" sizes="32x32" href="/icons/a-32.png">
<link rel="icon" type="image/png" sizes="16x16" href="/icons/b-16.png">
<link rel="icon" type="image/x-icon" href="/icons/c.ico">
<link rel="apple-touch-icon" sizes="180x180" href="/icons/d-180.png">
<link rel="mask-icon" href="/icons/e.svg" color="#4f46e5">
<link rel="manifest" href="/site.webmanifest">

The favicon.ico at the site root was a *seventh*, undeclared candidate. Every candidate was given a visually distinct solid colour so the chosen one was unmistakable: A blue, B green, C amber, D red, E a black glyph, F (root ICO) violet, and the manifest icon pink. The ICO & Favicon Generator produced C and F plus the HTML snippet; the other files are plain single-colour PNGs.

The important conclusion from rounds A–D: /favicon.ico is a fallback, not a competitor. A lot of "my new icon isn't showing" reports come from people replacing the root ICO while an old <link rel="icon"> still points at a cached PNG. The root file was never in the race.

What sizes really does

The sizes attribute is advisory. It tells the host "here is a 32 px bitmap" so it can pick a close match without downloading everything. It does not force the host to use that file at exactly that size, and it does not prevent the host from downscaling a larger declared file when a 16 px tab needs a bitmap. In round F the only declared icon was 64 × 64 and it still appeared in a 16 px tab, just softer.

This is why a single sizes="32x32" declaration plus a multi-size ICO is a sane, low-maintenance setup: the declared PNG handles the common tab case, and the ICO covers hosts that ask the container directly. Adding eight overlapping <link> tags mostly adds ambiguity, not quality.

type behaves similarly. It is a hint about the bytes behind the URL. Declaring type="image/x-icon" on a file that is actually a renamed PNG will not break every browser, but it will break some, and it makes debugging miserable. The generator emits the correct type for each output, which is a small detail with an outsized effect on consistency.

The three separate icon systems

The single most useful mental model from this experiment is that there are three almost-independent subsystems:

  1. Tab / bookmark icons — <link rel="icon"> and the implicit /favicon.ico fallback. Bitmap, chosen by declaration order plus sizes.
  2. Home-screen / install icons — apple-touch-icon on iOS, icons in the web manifest on Android and desktop PWA. Different sizes, different cropping, different caching.
  3. Pinned / monochrome surfaces — mask-icon in Safari, and platform-specific monochrome variants. SVG, not bitmap.

People routinely try to fix a problem in subsystem 2 by editing a file in subsystem 1. Round G and round H are the proof: deleting the apple-touch-icon and the manifest icons changed nothing in the desktop tab, and conversely editing favicon.ico changed nothing on the iOS home screen. If you take one thing from this article, take this separation.

Why "I replaced the file but the old icon is still there" is not a file problem

Favicons are cached aggressively and, in several hosts, cached separately from the page. Replacing the bytes at the same URL is the one operation most likely to be ignored. Our rounds only produced clean results because we used a fresh profile each time; when we repeated round A in a warm profile, the *previous* round's colour persisted through two hard reloads.

Practical order of operations when updating a live site:

  1. Change the URL, not only the bytes — add a version query or a new filename (/icons/a-32-v2.png).
  2. Update every declaration, including apple-touch-icon and the manifest array. A stale manifest entry keeps installing the old icon.
  3. Request a re-crawl in Search Console if the icon appears in search results; that cache is separate again.
  4. On mobile, delete and re-add the home-screen shortcut. iOS caches the rendered icon at install time and will not re-read the file.
  5. Only then clear your own browser cache to verify locally.

A 301 redirect on /favicon.ico deserves a special warning. The implicit fallback fetch is one of the least tolerant requests a browser makes; a redirect to a URL that returns 404, or a redirect chain, frequently results in no icon at all rather than an error message. Keep the root ICO as a direct 200 response. Our own Worker normalises legacy .html paths with a single 301, but deliberately leaves machine files and the root ICO out of that rewrite for exactly this reason.

Reading the generated HTML snippet

The ICO & Favicon Generator emits a small block of <link> tags alongside the ICO. Here is what each line is doing, in the order it appears:


<link rel="icon" href="/favicon.ico" sizes="any">
<link rel="icon" type="image/png" sizes="32x32" href="/favicon-32x32.png">
<link rel="icon" type="image/png" sizes="16x16" href="/favicon-16x16.png">
<link rel="apple-touch-icon" sizes="180x180" href="/apple-touch-icon.png">

sizes="any" on the ICO tells the host the container can supply whatever size it needs — which is true only because the file really contains six entries. The two PNG lines give crisp bitmaps for the two most common tab sizes without asking the host to unpack the container. The apple-touch-icon line is the *only* one of the four that iOS home screens read.

If you hand-write these tags instead, keep the order and keep the type values accurate. If you use the generator, paste the whole block — removing the sizes="any" line and keeping only the PNGs is a common cause of blurry large icons in Explorer.

Run the experiment yourself

  1. Download the six-size ICO and the specimen PNG.
  2. Create seven visually distinct single-colour icons (any image editor will do; you can also use our Colour Adjust tool to tint copies of the same PNG).
  3. Put the snippet from the setup section into index.html, add a minimal site.webmanifest with a 192 and a 512 entry, and serve the folder with python3 -m http.server 8787.
  4. Open a fresh browser profile for each round. Delete one file, reload, note the colour in the tab.
  5. Write down the order you observe. If it differs from our table, note the browser and OS version — that difference is itself useful information, and it is the kind of first-hand detail worth publishing.

The point of publishing a method rather than just a conclusion is that the answer can drift. A browser update may change how sizes is weighted, or how the manifest interacts with the tab icon. A ten-minute deletion test tells you the current truth about *your* stack, which is more valuable than a priority list copied from a 2019 blog post.

Appendix E — Timed cache rounds

The deletion rounds used fresh profiles. Repeating them in a warm profile produced a different story, and that difference is the actual explanation behind most "my favicon will not update" reports.

Two conclusions. First, a hard reload is not a favicon cache bust — the icon fetch is cached separately from the document. Second, changing the URL is the only reliable, user-independent fix. That is why every HTML snippet our generator emits can be given a -v2 suffix without touching the ICO logic.

There is a second cache that people forget: the search-result icon. Even after your own browser and your visitors' browsers have the new file, the icon shown in search results can lag until the crawler re-fetches it. That cache is controlled by a re-crawl request, not by anything in your HTML.

Appendix F — The manifest, field by field

The minimal manifest we used in the experiment is short enough to reason about completely:


{
  "name": "PicStudio Lab",
  "icons": [
    { "src": "/icons/m-192.png", "sizes": "192x192", "type": "image/png" },
    { "src": "/icons/m-512.png", "sizes": "512x512", "type": "image/png" },
    { "src": "/icons/m-maskable.png", "sizes": "512x512", "type": "image/png", "purpose": "maskable" }
  ]
}

src is resolved relative to the manifest URL, so a manifest served from /site.webmanifest with src: "icons/m-192.png" points at /icons/m-192.png; get this wrong and every entry silently 404s. sizes must match the real pixel dimensions — a 192 file labelled 512 is a common cause of an install card showing a blurry icon. type must describe the bytes. purpose: "maskable" marks the entry that is allowed to be cropped by an adaptive mask; the other entries are expected to be used as-is.

In our rounds, deleting the manifest changed nothing in the desktop tab (round H) but changed the install card completely. That is the cleanest demonstration that the manifest is a separate subsystem. It also explains why updating favicon.ico alone never fixes a stale PWA icon: the manifest array still points at the old filename.

Appendix G — Migrating an existing site without breaking anything

If the site already has an icon set, do the replacement in this order:

  1. Inventory. Write down every rel="icon", apple-touch-icon, mask-icon, manifest icons entry and the root favicon.ico. Most stale-icon bugs are one line in this inventory that nobody remembered.
  2. Add the new files under new names. Do not overwrite in place. Use -v2 or a dated suffix.
  3. Update every declaration in one commit. A partial update produces a site where the tab is new and the home screen is old, which is harder to diagnose than either state alone.
  4. Keep the root ICO as a direct 200. Do not let a general .html normalisation rule or a redirect chain touch it; the implicit fallback fetch is unforgiving.
  5. Verify with a fresh profile and with a real device for the home-screen case.
  6. Record the date and the file names in your release note. Six months later that note is the only evidence of what you shipped.

That procedure is the operational version of the 12-cell QA sheet, cell 12 in particular.

Appendix H — Why we publish the method instead of only the table

Browser behaviour around sizes, manifest interaction and icon caching has changed before and will change again. A priority list copied from an old article is a snapshot with no expiry date; a ten-minute deletion test is a measurement you can re-run on your own stack. The maintenance record states when these rounds were run and what would trigger a re-run. That is the difference between a reference page and a claim.

Frequently asked questions

Does <link rel="icon"> override /favicon.ico?

Yes. In our rounds any declared <link> won, and the root ICO was used only after all declared tags were removed. It is a fallback, not a competitor.

Why won't my favicon update after I replace the file?

Favicons are cached separately from pages. Change the URL (a version query or new filename), update apple-touch-icon and the manifest too, then re-add any mobile home-screen shortcut.

Do multiple sizes values make the browser pick the best one?

They are hints. The host may still pick the first declared icon and downscale it. Keep the declarations small and unambiguous.

Why is apple-touch-icon ignored in my desktop browser?

Because it serves iOS home-screen icons. Desktop tabs use rel="icon". They are separate subsystems.

Can I just put everything in one big ICO?

For tab and Windows surfaces, a six-size ICO covers a lot. It will not replace apple-touch-icon, manifest icons, or the mask-icon SVG — those are different files read by different hosts.

Image glossary

Ten terms that explain most “why does my image look wrong” problems. Each entry covers what it is, when you meet it, what this site does, and one common misconception.
<p><strong>DPI</strong> (dots per inch) describes how many ink dots a printer places in an inch. <strong>PPI</strong> (pixels per inch) describes how many image pixels sit in an inch. A 3000×2000 file tagged 72 DPI and the same file tagged 300 DPI contain exactly the same pixels; only the physical print size changes — about 105.8 cm wide at 72 DPI versus 25.4 cm at 300 DPI.</p> <p>You meet this when a print shop asks for “300 DPI”, a form asks for “295×413 px”, or an image jumps in size inside Word. To check whether a file is enough, multiply the target print size in inches by the target PPI: a 6-inch print at 300 PPI needs 1800 px of width.</p> <p>On this site, <a href="/tools/resize">Resize Image</a> changes pixels, <a href="/tools/id-photo">Rotate &amp; Flip</a> and <a href="/tools/crop">crop</a> cut to pixel sizes, and <a href="/tools/to-pdf">Images to PDF</a> lays pages out at A4. None of them invents detail.</p> <p class="myth"><strong>Common misconception:</strong> raising the DPI number from 72 to 300 does not sharpen anything; it only makes the image smaller in layout software.</p>Print dot density versus image pixel density — and why pixels are what matter.<p><strong>EXIF</strong> stores camera model, aperture, shutter speed, ISO and capture time. Phones also write GPS latitude, longitude, altitude and direction. The block travels inside JPEG, TIFF and HEIC files; PNG stores no EXIF by default. Cropping, compressing or converting does not necessarily remove it.</p> <p>It matters when you send an original to a group chat, post a photo on a forum, or sell a camera. Reading the file's “properties” is not always enough — use a viewer that lists the tags.</p> <p>Our <a href="/tools/exif">EXIF Viewer &amp; Cleaner</a> parses the file in the browser, lists the entries, and re-encodes an export without them. Stripping is irreversible, so keep the original.</p> <p class="myth"><strong>Common misconception:</strong> social platforms always strip metadata. Policies differ and change; do not rely on them for originals.</p>Camera settings and location data written into the file — often surviving edits.<p>sRGB, Display P3 and Adobe RGB are different gamuts. An <strong>ICC profile</strong> tells software how to map numeric values to real colours. Without a profile, browsers usually assume sRGB. A P3 file opened by software that ignores the tag can look dull or oversaturated.</p> <p>You meet this when a design looks vivid on a Mac and grey on Windows, when a camera exports Adobe RGB straight to the web, or when a printer asks for CMYK.</p> <p>Our tools work in sRGB on canvas and export PNG/JPEG without a custom profile — a safe default for screens. For print, convert to CMYK and embed the target profile in a desktop editor.</p> <p class="myth"><strong>Common misconception:</strong> adding an sRGB tag fixes wrong colours. A tag only explains the numbers; it does not change them.</p>The tag that says what your RGB numbers actually mean.<p><strong>Alpha</strong> is the transparency channel. Straight alpha stores (R,G,B,A); <strong>premultiplied</strong> alpha stores (R×A, G×A, B×A, A). Browsers composite with premultiplied values internally. If scaling or blurring multiplies twice, semi-transparent edges pick up halos.</p> <p>You see it when a transparent PNG looks grey after shrinking, an icon on a dark background gains a white outline, or a transparent image converted to JPEG gets a black fringe. JPEG has no alpha, so something must fill the empty area.</p> <p>Our editing tools export PNG with transparency intact. Choose a background colour before converting to JPEG. The icon tool writes a transparent ICO; the rounded-corner tool writes transparent corners.</p> <p class="myth"><strong>Common misconception:</strong> transparency “automatically becomes white” in JPEG. It depends on the encoder and is often black.</p>Transparency channels, and why edges turn white, black or grey.<p><strong>Bit depth</strong> is how many bits each channel uses. 8 bits per channel gives 256 levels and about 16.7 million colours; 16 bits gives far finer steps and is used for RAW, scanning and print retouching. Browser canvas is effectively 8-bit, so anything wider is quantised.</p> <p>You meet it when a sky gradient shows visible bands, a black-and-white conversion breaks into steps, or a 16-bit TIFF shrinks dramatically after passing through a web tool.</p> <p>Our tools process and export 8-bit PNG/JPEG — enough for screens and social. Keep the original 16-bit file if you plan more print retouching.</p> <p class="myth"><strong>Common misconception:</strong> 8-bit is always insufficient. For screen output it is usually fine; repeated lossy compression causes more damage.</p>8-bit versus 16-bit colour, and where banding comes from.<p><strong>Lossy</strong> compression discards detail the eye is less likely to notice; <strong>lossless</strong> compression only reorganises data so the original can be rebuilt exactly. JPEG is lossy, PNG is lossless, WebP supports both. Every lossy re-save loses a little more — generational loss.</p> <p>You see it when a screenshot saved as JPEG has soft text, a logo shows blocky edges, or a file edited ten times keeps getting worse. Use PNG or high-quality WebP when text and hard edges matter.</p> <p>Our <a href="/tools/compress">compressor</a> re-encodes with a quality setting and optional width limit; <a href="/tools/convert">Convert Format</a> offers JPG, PNG and WebP. For text, prefer PNG; for photos, JPEG at 70–85 is usually enough.</p> <p class="myth"><strong>Common misconception:</strong> saving a JPEG as PNG restores quality. Lost detail does not come back; it merely stops getting worse.</p>What JPEG throws away, what PNG keeps, and why re-saving hurts.<p>A <strong>gamut</strong> is the range of colours a device or colour space can represent. sRGB is narrow but universal; Display P3 is wider and shows more saturated greens and reds. A wide-gamut file shown by sRGB-only software looks oversaturated; the reverse looks dull.</p> <p>You meet it with P3 phone photos uploaded to a website, fluorescent design colours that cannot be printed, or two laptops showing the same file differently.</p> <p>Our tools process and export in sRGB, which suits the web, social media and office documents. For print or wide-gamut delivery, finish colour management in a professional editor.</p> <p class="myth"><strong>Common misconception:</strong> a wider gamut is always better. On the web, colours outside sRGB simply disappear on many devices.</p>Why the same file looks different on two screens, and why sRGB is the web default.<p><strong>Raster</strong> images (PNG, JPEG, WebP) are grids of pixels; enlarging beyond the original resolution softens them. <strong>Vector</strong> images (SVG, AI, EPS) are paths and fill rules and scale without loss. Browsers display SVG, but favicons and some system icons still require bitmaps.</p> <p>You meet it when a small logo is blown up for a poster, a screenshot is treated as vector art, or an “SVG” turns out to contain an embedded bitmap.</p> <p>This site works on raster images, with pixel caps on resize, crop and upscale. The icon tool writes a multi-size ICO; make the SVG in a vector editor and use this site for the bitmap fallbacks.</p> <p class="myth"><strong>Common misconception:</strong> a .svg extension guarantees vector content. It may be a wrapped PNG.</p>Pixels versus paths, and when enlarging is hopeless.<p>Canvas pixels live in memory at four bytes each: 4000×4000 is 64 MB, 8000×8000 is 256 MB. Browsers also cap the maximum side and total area. Chrome usually allows up to 16384 px per side; Safari and mobile are lower and vary by device.</p> <p>You hit the limit when stitching a very long screenshot, enlarging a scan, or rendering many PDF pages at once. Symptoms include a black preview, a zero-byte export, or a frozen tab.</p> <p>Our editing tools cap the working side at 3000 px and crop/upscale at 4000 px; larger requests are scaled down first. Split long images into parts and stitch afterwards.</p> <p class="myth"><strong>Common misconception:</strong> a machine with more RAM cannot fail. Browsers also have per-canvas area and GPU texture limits.</p>Why very large images fail silently, and the caps this site applies.<p><code>canvas.toDataURL()</code> and <code>toBlob()</code> support image/png, image/jpeg and image/webp. JPEG has no alpha, so transparent areas get a fill. WebP may fall back to PNG on old Safari. ICO, PDF and SVG are not canvas formats.</p> <p>You notice problems when an export grows unexpectedly, transparency turns black, the extension does not match the real encoding, or a data URL pasted into CSS bloats the page.</p> <p>Our editing tools export PNG by default; Convert Format offers JPG/WebP/ICO; Images to PDF re-wraps pages with a PDF library; the Base64 tool produces a PNG data URL. Extensions always match the encoding.</p> <p class="myth"><strong>Common misconception:</strong> renaming .png to .jpg converts it. The bytes are unchanged and upload forms still reject it.</p>PNG, JPEG and WebP are native; ICO, PDF and SVG are not.

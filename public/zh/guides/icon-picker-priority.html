浏览器到底用了哪个 favicon：一次删一个文件的八轮实测

发布于 2026-11-20 · 阅读约 10 分钟

上一篇看的是图标被宿主选中之后发生了什么，这一篇看"选中"本身。页面里既有 <link rel="icon">，根目录又躺着 /favicon.ico，还有 apple-touch-icon，manifest 里又列了几个尺寸——标签上到底显示哪一个？删掉其中一个，又会怎样？

实验设置：六个声明，加一个没声明的

我们在 http://localhost:8787 上起了一个本地页面，摆了六个候选文件。用真实 origin 很重要：file:// 页面不会走同一套 favicon 缓存，有些宿主干脆拒绝从文件 URL 取图标。

六个文件全部用 <link> 声明，而站点根目录的 favicon.ico 是第七个、未被声明的候选。每个候选都给一种一眼能分的纯色：A 蓝、B 绿、C 琥珀、D 红、E 黑色字形、F（根 ICO）紫，manifest 图标粉。C 和 F 由本站 ICO 生成器产出，其余是单色 PNG。

<link rel="icon" type="image/png" sizes="32x32" href="/icons/a-32.png">
<link rel="icon" type="image/png" sizes="16x16" href="/icons/b-16.png">
<link rel="icon" type="image/x-icon" href="/icons/c.ico">
<link rel="apple-touch-icon" sizes="180x180" href="/icons/d-180.png">
<link rel="mask-icon" href="/icons/e.svg" color="#4f46e5">
<link rel="manifest" href="/site.webmanifest">

八轮，每次只动一处

每一轮只删掉或只改动一样东西，然后用全新的浏览器配置打开页面，记录标签的颜色。全新配置是关键：复用配置看到的是缓存里的答案，不是当下的答案。

轮次改动标签显示说明了什么
A什么都不删A（32 px，第一个带 sizes 的声明）声明过的 <link rel="icon"> 完全压过根目录 /favicon.ico
B删掉 A 的文件B（16 px）浏览器顺延到下一个声明的 <link>，不会跳去根 ICO
C删掉 A 和 BC（声明过的 .ico）声明顺序依然优先，宿主并不偏爱"原生"的 ICO
D删掉三条 <link>，保留根文件F（紫色根 ICO）根 /favicon.ico 是隐式兜底，不是首选
E声明两条不带 sizes 的 <link>先声明的那条没有 sizes 提示时，顺序决定结果
F只声明 sizes="64x64"，标签要 16 px那张 64 px，被缩小sizes 是提示而非硬约束，宿主会自己缩放
G删掉 apple-touch-icon，看桌面标签不变apple-touch-icon 对桌面标签完全不可见
H删掉 manifest 图标，看桌面标签不变manifest 图标服务安装和 PWA 场景，不进标签

手机上另跑了两轮：I 轮在有 D 的情况下添加到主屏，图标是 D（180 px），iOS 只读 apple-touch-icon，无视标签那套 <link>；J 轮删掉 D 只留 manifest，Android 用 manifest 图标，iOS 则退化成网页截图。

A 到 D 最重要的结论只有一句：/favicon.ico 是兜底，不是竞争者。大量"我的新图标不显示"的反馈，其实是有人替换了根 ICO，而页面里一个旧的 <link rel="icon"> 还指向缓存中的 PNG。根文件从来没进过这场比赛。

sizes 到底管什么

sizes 是建议值。它告诉宿主"这是一张 32 px 位图"，宿主据此挑一个接近的，不必把每个候选都下载一遍。它不强制宿主按这个尺寸使用，也不阻止宿主把更大的声明文件缩给 16 px 标签。F 轮里唯一声明的是 64×64，它照样出现在 16 px 的标签上，只是更软。

所以"一个 sizes="32x32" 的 PNG，加一个多尺寸 ICO"是很省心的组合：声明的 PNG 应付最常见的标签，ICO 留给直接向容器要图的宿主。叠八条互相重叠的 <link>，主要是在制造歧义，不会提高质量。

type 的行为类似，它描述 URL 背后是什么字节。给一张实际是改了后缀的 PNG 标上 type="image/x-icon"，不是每个浏览器都会坏，但会坏掉一部分，而且让排查变得很难受。生成器会按每种输出给正确的 type，这是小细节，对一致性影响却很大。

三套几乎独立的图标系统

这次实验最有用的心智模型，是把图标分成三套互不相干的子系统：

  1. 标签与书签图标。 <link rel="icon"> 加上隐式的 /favicon.ico 兜底。位图，按声明顺序和 sizes 挑。
  2. 主屏与安装图标。 iOS 的 apple-touch-icon，Android 和桌面 PWA 的 manifest icons。尺寸、裁切、缓存规则都不一样。
  3. 固定标签与单色表面。 Safari 的 mask-icon，以及平台各自的单色变体。是 SVG，不是位图。

人们常常拿第一套里的文件去修第二套的问题。G 轮和 H 轮就是证据：删掉 apple-touch-icon 和 manifest 图标，桌面标签一点没变；反过来只改 favicon.ico，iOS 主屏也一点没变。

如果整篇只记住一件事，记这个分家。它比任何优先级列表都更省时间。

"换了文件旧图标还在"，问题不在文件

favicon 缓存很顽固，而且在不少宿主里和页面分开缓存。在同一个 URL 上替换字节，是最容易被忽略的操作。我们的轮次能出干净结果，全靠每轮换新配置；如果在热的配置里重跑 A 轮，上一轮的颜色扛过了两次强制刷新。

替换文件后热配置，URL 不变热配置，URL 带版本
立即刷新上一轮的颜色新颜色
强制刷新（Ctrl/Cmd+Shift+R）上一轮的颜色新颜色
过 2 分钟开新标签上一轮的颜色新颜色
换全新配置新颜色新颜色
清除站点数据后新颜色新颜色

两个结论。第一，强制刷新不是 favicon 的缓存清除，图标的抓取和文档是分开缓存的。第二，改 URL 才是唯一可靠、不依赖用户操作的修法。所以生成器输出的每个文件名都可以加 -v2 后缀，而不必动 ICO 本身的逻辑。

上线更新时按这个顺序做：先把 URL 改掉，不只是改字节，可以加版本参数或者换文件名，例如 /icons/a-32-v2.png；再把所有声明一起改，包括 apple-touch-icon 和 manifest 数组，留一条旧的就会继续装旧图标；图标会出现在搜索结果里的，去 Search Console 请求重新抓取，那又是另一层缓存；手机上去掉主屏快捷方式再重新添加；最后才清自己的浏览器缓存做本地验证。

根 ICO 上不要放 301

这一条值得单独拎出来。/favicon.ico 上的重定向要特别小心：隐式兜底请求是浏览器最不宽容的请求之一，跳到一条返回 404 的地址，或者跳转链太长，经常直接变成"没有图标"，连个错误提示都没有。

把根 ICO 保持成直接返回 200 的文件。我们自己的站点会用一条 301 统一旧的 .html 路径，但刻意把机器读取的文件和根 ICO 排除在这条规则之外，原因就是这个。

看懂生成器给的那段标签

ICO 生成器除了文件，还会吐一小段 <link>。逐行看它在做什么：

<link rel="icon" href="/favicon.ico" sizes="any">
<link rel="icon" type="image/png" sizes="32x32" href="/favicon-32x32.png">
<link rel="icon" type="image/png" sizes="16x16" href="/favicon-16x16.png">
<link rel="apple-touch-icon" sizes="180x180" href="/apple-touch-icon.png">

sizes="any" 是在告诉宿主：这个容器你要多大有多大。这句话只有在文件里真的装了六个条目时才成立。两条 PNG 给最常见的两种标签尺寸提供清晰位图，省得宿主去解容器。四条里只有 apple-touch-icon 那一行会被 iOS 主屏读取。

手写这些标签的话，顺序照抄，type 写准。用生成器的话，整段贴进去——删掉 sizes="any" 只留 PNG，是资源管理器里大图标发虚的常见原因。

manifest 逐字段看

实验里用的最小 manifest 短到可以完全讲清楚：

{
  "name": "PicStudio Lab",
  "icons": [
    { "src": "/icons/m-192.png", "sizes": "192x192", "type": "image/png" },
    { "src": "/icons/m-512.png", "sizes": "512x512", "type": "image/png" },
    { "src": "/icons/m-maskable.png", "sizes": "512x512", "type": "image/png", "purpose": "maskable" }
  ]
}

src 是相对 manifest 的 URL 解析的。所以从 /site.webmanifest 提供、里面写 "icons/m-192.png"，实际指向 /icons/m-192.png；写错就是每一条都静默 404。sizes 必须和真实像素一致，把 192 的文件标成 512，是安装卡图标发虚的常见原因。type 要描述字节。purpose: "maskable" 标记的是允许被自适应遮罩裁切的那一条，其余条目应当原样使用。

删掉 manifest，桌面标签毫无变化（H 轮），安装卡却完全变了。这是"manifest 是独立子系统"最干净的演示。它也解释了为什么只换 favicon.ico 永远修不好过期的 PWA 图标：数组里还指着旧文件名。

老站换图标，按这个顺序走

站点已经有图标集的话，按这个顺序换，能把"新旧混着"的时间压到最短。

  1. 先清点。 每一个 rel="icon"、apple-touch-icon、mask-icon、manifest 条目和根 favicon.ico 都写下来。多数"图标不更新"的 bug，就是清单里漏了一行。
  2. 新文件用新名字。 用 -v2 或日期后缀，不要原地覆盖。
  3. 一次提交改完所有声明。 改一半会得到"标签是新的、主屏是旧的"这种更难诊断的中间态。
  4. 根 ICO 保持直接 200。 别让通用的路径规范化规则或跳转链碰到它。
  5. 用全新配置和真机验证。 主屏那一格必须上真手机看。
  6. 把日期和文件名写进发布记录。 半年后这就是你发货的唯一证据。
症状属于哪套系统先查什么
换文件后还是旧图标标签缓存URL 是否变了？manifest 一起改了吗？
标签正常，主屏不对主屏与安装apple-touch-icon 与 manifest 的 icons 数组
Safari 固定标签是通用字母单色表面缺 mask-icon 的 SVG
有些页面完全没有图标兜底/favicon.ico 是否直接 200，所有 href 是否都活着
只有资源管理器大图标糊容器ICO 里真的有 128 / 256 两条吗？

发布方法而不只发布结论，是因为结论会漂移。浏览器更新可能改变 sizes 的权重，manifest 和标签图标之间怎么互动也可能变。十分钟的删除测试能告诉你自己这套技术栈当下的真相，比抄一份旧文里的优先级列表可靠。

常见问题

link rel="icon" 会覆盖 /favicon.ico 吗？
会。我们的每一轮里，只要声明了就由声明的 link 胜出，根目录 ICO 只在所有声明标签都被删掉之后才出现。它是兜底，不是竞争者。
替换了文件，favicon 为什么还不更新？
favicon 和页面是分开缓存的。改 URL（加版本参数或换文件名），同时更新 apple-touch-icon 和 manifest，手机上还要删掉主屏快捷方式重新添加。
写多个 sizes 值，浏览器会挑最合适的那个吗？
那是提示。宿主仍可能直接用最先声明的那一张再缩放。声明越少越明确，效果越稳定。
桌面浏览器为什么忽略 apple-touch-icon？
因为它服务的是 iOS 主屏图标。桌面标签用 rel="icon"，两套是彼此独立的子系统。
能不能把所有东西塞进一个大 ICO？
标签页和 Windows 的各种表面，六档 ICO 能覆盖大部分。但它替代不了 apple-touch-icon、manifest 图标和 mask-icon 的 SVG，那些是不同宿主读的不同文件。

「我的透明 PNG 有黑底」在工单里是一句话，在技术上是至少六种不同的故障。文件可能完好，是查看器在骗你；alpha 可能在某次另存时被丢掉；alpha 明明正确，透明像素底下的 RGB 却已经脏了；也可能文件在到你屏幕之前，被另一个程序整体重编码过一遍。

这是一份事故鉴定报告，不是 alpha 通道的名词解释。我们做了一枚边缘故意羽化的标本，把它推过人们真正会走的路径：图片查看器、文字处理软件、格式转换、聊天软件、Base64 往返、圆角处理，然后只看边缘给结果分类。因为边缘会告诉你坏在哪一层。

先看这一张

四种都曾被报告成「我的 PNG 有背景」：棋盘格上的正确 alpha、压成黑底、压成白底、以及预乘错误造成的暗晕。只有前两种里，有一种是文件真的坏了。

标本与为什么必须用软边

硬边圆形会把预乘错误藏起来：每个像素要么全不透明、要么全透明，透明像素底下哪怕 RGB 是错的也永远不会露出来。所以标本是一枚 420 px 的实心蓝圆，但边缘的 alpha 在约 14 px 内逐渐衰减。这段渐变就是测量仪器。

判断方法很朴素：把图放在浅色和深色两种底色上各看一次。半透明环如果发暗、发灰、发脏，说明 RGB 与 alpha 没对齐；如果渐变突然变成硬台阶，说明 alpha 被拍平了。标本可下载为 picstudio-soft-alpha.png，下面每一步都能自己重跑。圆角对照另用 硬边标本。

故障一：错的是查看器，不是文件

最省钱的误判。很多查看器不用棋盘格表示透明，而是用纯黑或纯白画布。同一个文件在 A 软件里黑底、在 B 软件里棋盘格，背景跟着软件走，就说明 alpha 还在，只是画布颜色不同。

验证只要两步：换第二个程序打开，或者把图放进一张有颜色的网页。若底色随程序变、边缘的羽化仍在，立刻停止修图——这时候去「修透明」只会把一个好文件改坏。我们把这一类排在第一位，就是因为它最常被当成文件损坏。

故障二：容器根本装不下 alpha

JPEG 没有 alpha 通道，导出时会先拿一个颜色把透明区域填实，通常是黑或白，再编码。这个过程不可逆：填充色已经烤进像素里了，之后无论转回 PNG 多少次都不会自己长回透明。

识别特征是整片实心底色 + 边缘硬台阶，羽化完全消失。这类只能回到还带 alpha 的上一版源文件重新导出，或者重建蒙版。本站 格式转换 能阻止「再存一次又变 JPEG」，但救不回已经丢掉的通道，这一点页面里也写明了，不做什么「一键还原透明」的承诺。

故障三：调色板 PNG 的 1 位 tRNS

PNG 的调色板模式可以用 tRNS 块指定某个索引透明，但它是 1 位开关：要么全透，要么不透，没有中间值。把带羽化边的图存成调色板 PNG，软边会被量化成锯齿状的一圈。

它和故障二的区别在边缘：底色未必是纯色，但羽化变成了颗粒状的二值台阶，放大看能数出像素。处理方式是重新编码为真 RGBA，而不是继续调「透明度」滑杆。这类问题在老式导出流程和图标工具里最常见。

故障四：预乘 alpha 造成的暗晕

这一种最容易被误报成「黑底」，其实黑底并没有铺满，只是软边外圈多了一圈灰黑细线。原因是预乘 alpha 的数据被当成直通 alpha 来合成，或者半透明像素底下的 RGB 被提前压暗过。合成时颜色被乘了两次，边缘就脏了。

判别只看边缘：有晕＝数学错了，整片实色＝alpha 没了。修复是重新编码为干净的 RGBA，让透明像素底下的 RGB 与相邻不透明像素一致，而不是给整张图加亮度。本站 色彩调整 用来观察曲线变化，不会偷偷改写 alpha。

故障五：圆角与描边操作留下的脏 RGB

圆角处理把四角的 alpha 置零，却常常把那几个像素原来的 RGB 留在原地。在浅底上看不出，一放到深底上，四角就冒出深色三角或暗边。描边、羽化、阴影同理。

这是「alpha 正确、RGB 过期」，跟前面几类都不同。用硬边标本走一次 圆角，再分别在白底和黑底上截图对照，就能复现。解法同样是干净重编码：让全透明像素继承邻近颜色，别留下任意值。

故障六：别人替你重新编码了一次

聊天软件、文档协作、邮件客户端为了压缩体积，常把 PNG 转成 JPEG 或重新压一遍。发送方看到的是好的，接收方拿到的是被拍平的版本。于是工单变成「我这边明明是透明的」。

这类故障的特点是同一次传递里两份文件不一致。要证明它，别争，直接比对发送前后两份文件的字节数与是否还有 alpha 块。Base64 往返本身不丢透明——它是逐字节的文本编码——如果转完 Base64 透明没了，问题出在 CSS 底色或 canvas 导出那一步，不在编码。

边缘优先的判别顺序

把上面六类压成一条从上往下的流程，避免一上来就动文件：

  1. 换第二个查看器 / 换有色底 → 背景跟着程序变？故障一，停手。
  2. 整片实色且羽化消失？故障二，回去找源。
  3. 边缘是颗粒状二值台阶？故障三，重编码为 RGBA。
  4. 只有一圈灰黑细晕？故障四，修 RGB 与预乘。
  5. 只在圆角/描边处出现暗角？故障五，清脏 RGB。
  6. 发送前后两份不一样？故障六，换传递方式。

顺序不能反。先排除查看器，是因为它零成本且最常见；一上来就重新导出，反而可能把唯一一份带 alpha 的原稿覆盖掉。

本站每个工具实际改了什么

把话说死，省得误用：格式转换 改容器与颜色模式，不凭空造 alpha；色彩调整 改 RGB 曲线，保留通道；圆角 改四角 alpha，需要配合干净编码；元数据 只动元数据块，不碰像素。所有处理都在浏览器本地完成，不上传文件，这一点也决定了我们可以把每一步的字节差异公开写进报告里。

一次完整的修复走查

拿标本走一遍：白底看一次 → 黑底看一次 → 确认是暗晕而非实底 → 用转换页重存为 RGBA PNG → 回两色底再看 → 若四角仍有暗三角，单独重做圆角 → 最后另存一份，比对文件大小与是否仍含 alpha。每一步都留截图，报告里的数字就是这么来的，不是估的。

我们故意没测什么

没测打印驱动、没测某个特定版本的办公套件、没测带 ICC 配置文件的极端组合。不是遗漏，是这些变量一多，结论就没法复现。我们把范围收在「浏览器里能自己重跑」的路径上，读者拿同一份样本应当得到同一组结果。

附：可复现的样本与十行验收脚本

样本：软边标本、硬边标本。验收不必装环境，浏览器控制台里读回 canvas 的四个角与边缘中点，检查 alpha 是否为 0 / 255 / 中间值三档，再看半透明处的 RGB 是否与邻近不透明像素接近。十行以内能写完，判定规则写在上面第六节。

常见问题

同一个 PNG 在 A 软件黑底、B 软件棋盘格，是哪个坏了？

都没坏，是画布颜色不同。换有色网页看一眼即可。

存成 JPEG 之后还能把透明找回来吗？

不能。填充色已写进像素，只能从带 alpha 的原稿重导或重建蒙版。

软边外一圈细黑线是什么？

多半是预乘 alpha 被当直通 alpha，或半透明像素底下 RGB 偏暗，和整片黑底不是一回事。

转 Base64 会丢透明吗？

不会，Base64 是逐字节编码。透明没了去查 CSS 底色或 canvas 导出。

圆角出现深色三角怎么修？

四角 alpha 置零时底下的 RGB 没清。重编码为干净 RGBA，再在深浅两底上各看一次。

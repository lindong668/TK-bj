透明 PNG 变黑、变白、长黑边：六种事故分类

发布于 2026-11-20 · 阅读约 11 分钟

「我的透明 PNG 有黑底」不是一个 bug，而是至少六个 bug 恰好被写进同一句话。文件可能是好的，只是查看器在说谎；也可能 alpha 早在某次保存里就没了。先看边缘，再动手改，顺序错了会把证据一起删掉。

一个标本，一条故意做软的边

文件本身可能正常，是查看器在撒谎；alpha 可能在某次另存里被扔掉；透明像素下面的 RGB 可能是错的；也可能是另一个程序在你看到它之前先转了一次码。这几种情况在工单里都叫「我的 PNG 有背景」，修法却彼此无关。这是一份事故报告，不解释 alpha 通道的定义。我们做了一个蓝色圆盘当标本，alpha 在约 14 px 内逐渐衰减。硬边查不出问题：每个像素非全透明即全不透明，透明区域下面写错的 RGB 永远不会露出来。柔边才是诊断工具——如果半透明环下面的 RGB 是错的，环就会发暗、发脏；如果被压平，渐变会变成贴着实色底的一条硬台阶。

标本可以下载下来自己复现：软边 Alpha 样本。圆角那一组换成实心 logo，因为那里要测的恰好是硬边。

事故一：查看器画的黑底，不是文件的黑底

有些查看器把透明画成白色，有些画成黑色，有些画棋盘格，还有些直接用应用主题色。文件在一个画黑底的软件里打开，看起来和被毁了 alpha 一模一样，但字节一个都没动。

判断方法很省事：同一个文件用两个不同软件打开，或者粘到一个有底色的网页里。背景跟着软件走，文件就是好的。这是最常见的一类假警报，动手之前先把它排除掉。

事故二：格式根本装不下 alpha

JPEG 没有 alpha 通道。透明 PNG 存成 JPEG，必须压到某个颜色上，不同编码器选的填充色还不一样：黑、白，或者透明区底下那堆本来就存在的 RGB 值，常常是垃圾。所谓「透明 PNG 在 Word 里变黑」，多半不是 Word 渲染的锅，而是导出那一步已经变成 JPEG 了。

同类问题还有部分 BMP 写入器、只保留 1 位透明标志的老式 GIF 导出，以及把图栅格化到白页上的 PDF 流程。判断时看真实格式和通道数，别看后缀。.png 后缀套着 JPEG 字节，比想象中常见，浏览器是嗅探内容的，不是看扩展名。

修法：用格式转换重新导出，输出选 PNG，或者带 alpha 的 WebP，中途不要过一次 JPEG。这个工具能输出 PNG、JPG、WebP 与 ICO，输入支持 PNG / JPG / WebP / GIF / BMP / SVG / AVIF / ICO / HEIC，其中 HEIC 只能作输入。

事故三：调色板 PNG 只有 1 位 tRNS

索引色（调色板）PNG 只能靠 tRNS 块表达透明，实质是一个透明调色板项。200 级 alpha 的柔边表达不了，量化会把它压成一条硬的、带锯齿的边界。结果看起来是白色或暗色的毛边加阶梯，而不是平滑过渡。

判断：边缘是锯齿而不是渐变，同时图像的颜色数量很少。重新存成 RGBA PNG 能修，再存一次调色板 PNG 不能。

这一条很容易被误诊成「抗锯齿没开」。它是色彩模式的限制，跟抗锯齿设置无关。

事故四：预乘 alpha 与那圈暗边

这条最值得看，也是标本必须留柔边的原因。直通（非预乘）alpha 里，像素把真实颜色和透明度分开存；预乘 alpha 里，存的 RGB 已经乘过 alpha。两种表示都合法，但必须标注清楚、全程一致。

流水线把预乘当直通处理、乘了两次、或者先把半透明像素下面的 RGB 压暗再合成到浅色背景上，柔边就会多出一圈暗色。它不是黑底：内部完全正常，只有过渡带脏。所以判断要看环，不看中心。均匀的暗色描边沿着柔边走，是预乘损坏；整个形状后面一整块实色，是压平问题。两种修法毫无关系，这就是「重新存成 PNG」这类万能建议经常失灵的原因。

算式很短。颜色 C、alpha a、背景 B，正确合成是 a·C + (1−a)·B。如果存的 C 已经乘过 a，合成时又乘一次，得到的是 a²·C + …，暗掉的量正好显示为光晕。柔边越宽，中招的像素越多。

修法：转成一份干净的 RGBA PNG，然后在浅色页和深色页上各看一次边。光晕还在，说明损坏发生在你拿到文件之前，必须回源编辑器用直通 alpha 重出。

事故五：圆角操作留下的暗三角

加圆角，就是把半径之外像素的 alpha 设成 0。如果工具只改 alpha、留着旧 RGB，某些查看器和后续流程会把那些残留颜色翻出来，四个角出现暗三角。这和事故四是同一类问题，只是落在硬边上。

判断：问题只出现在四个角，直边干净。

修法：先用圆角工具处理，再走一次格式转换，然后对着黑底和白底各看一遍角。

事故六：在路上被别人转码了

聊天软件、CDN 图像处理、邮件客户端、各种「上传前优化」的浏览器扩展，都会重新编码。透明 PNG 经过一条目标是 JPEG 或压平 WebP 的流水线，到对面就变成实色背景。发送方看到的是原图，接收方看到的是事故。

判断：对比两端的格式和体积。收到的是 JPEG、发出的是 PNG，任何渲染设置都救不回 alpha，它是在传输途中被丢掉的。

Base64 往返反而是无损的：字节转成文本再解回来，还是同一个 PNG，tRNS 和 ICC 块都在。Base64 图看起来丢了透明，通常是 <img> 上挂了 CSS 背景，或者 canvas 导出那一步压平了。把标本编码一次再解码一次，逐字节比对，就能证明编码这一步是清白的。

从边缘入手的判断顺序

按这个顺序走，每一步都比下一步便宜。

  1. 换一个查看器，放到有底色的页面上。背景跟着软件走，就是事故一，文件没问题，到此为止。
  2. 查真实容器和通道数。JPEG、BMP、压平的 WebP，就是事故二。
  3. 看边缘。整块实色铺在后面，是压平；锯齿阶梯，是事故三；只有一圈暗环，是事故四；只有四角发暗，是事故五。
  4. 比对发出和收到的文件。格式不同、体积小了一截，就是事故六。
  5. 到这一步才重新编码。在第 1 步之前就转存，会毁掉证据，通常连同 alpha 一起毁掉。

顺序就是取证的全部意义。大部分网上的建议直接从第 5 步开始，所以能修好一部分，也能把另一部分弄得更糟。

压缩要单独提醒一句：激进量化会把 RGBA PNG 转成调色板 PNG，悄悄把事故三带回来。压完柔边 logo 要看边，不能只看省了多少 KB。

修复演练、字节证据，以及修不了的部分

拿柔边标本，故意导出一份 JPEG 把它弄坏，再按顺序走：用格式转换载入损坏的 JPEG 并导出 PNG，会看到黑底已经烙进像素里——转换不可能凭空造出 alpha，这正是流程要从第 1 步开始的原因。回到原始 PNG，用圆角工具加一个半径，导出后在白页和黑页上检查四个角。把结果编码成 Base64 再解码，边缘应当完全一致。最后用 EXIF 清理工具剥掉元数据，alpha 不受影响，这能区分「清元数据」和「重编码像素」两件常被混为一谈的事。

最值得盯的是最后一行。读到 alpha 为 2 的像素，如果 RGB 是 (0,0,0) 而画面是蓝色，以后合成到白底就会出暗边；如果读到的是 (56,189,248)，文件就是对的，是查看器的问题。前一种情况只要源编辑器还这么写，重编码多少次都没用，只能回源头重出。

也要说清边界。重编码能修色彩模式、透明像素下残留的 RGB、容器选错；它修不回一次 JPEG 导出丢掉的 alpha，修不回已经压进背景的人脸，也修不回收件人手里那份被聊天软件转码过的副本。另一个容易忽略的前提：本站编辑类工具的工作画布长边上限是 3000 像素，超出会等比缩小，而且只导出 PNG，所以别拿超大原图在这里做像素级取证。

常见问题

为什么同一个透明 PNG，在一个软件里是黑底，在另一个里是棋盘格？
那是查看器自己画布的颜色，不是文件。换一个软件打开，或者贴到有底色的网页上；背景跟着软件变，说明 alpha 完好。
存成 JPEG 之后还能恢复透明吗？
不能。JPEG 没有 alpha 通道，压平时用的填充色已经写进像素里。只能回原始素材重新导出，或者重新做一张蒙版。
柔边外面那圈细细的暗边是怎么来的？
通常是预乘 alpha 被当成直通 alpha 处理，或者半透明像素下面的 RGB 被压暗过。它和「整块黑底」不是同一个故障。
PNG 转 Base64 会丢透明吗？
不会。Base64 是逐字节的文本编码，解回来还是同一份 PNG。透明消失要去看 CSS 背景或者 canvas 导出那一步。
圆角为什么会在四个角露出暗三角？
角的 alpha 被设成 0，但底下的 RGB 还是旧值。重新编码成干净的 RGBA PNG，再分别放到浅色和深色背景上检查四个角。

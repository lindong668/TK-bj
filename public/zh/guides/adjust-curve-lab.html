三个滑块，三条曲线：亮度、对比度与伽马实测

发布于 2026-11-20 · 阅读约 11 分钟

「调一下亮度」和「加一点对比度」听起来是无害的动作，实际每一个都在偷偷丢掉一部分像素值。先从哪一头开始坏、坏在哪个具体数值上，用工具自己公开的算式就能算清楚，不用靠眼睛猜。

先把算式抄下来，再看图

调色页有个少见的地方：它把每个滑块背后的算式直接印在页面上。亮度是给每个 RGB 通道加一个常数；对比度是 new = factor × (old − 128) + 128；饱和度先按 0.299R + 0.587G + 0.114B 算出 luma，再把颜色推离或拉向这个灰点；锐化用反锐化掩模，original + (original − blur) × strength。

四行算式就能解释大部分「照片怎么变成这样」的抱怨。下面拿一张色阶图逐格比对，每个数字都能复算。

色阶图是专门画来当量具的：一条从深蓝到亮橙的竖向渐变，六块灰阶 12 / 45 / 90 / 140 / 190 / 235，再加一个红块、一个绿三角、一个黄圆。每个元素都有已知的输入值，改动前后能量出来，而不是靠嘴说。另存了一份 JPEG 版本，用来把「重新编码的损失」和「滑块的影响」分开。

亮度是平移，先断的永远是高光

亮度滑块的范围是 −100 到 +100，工具会把它乘以 2.55，所以滑块 +16 约等于每个通道加 40 级。按加 40 级计算，每个像素的每个通道都加 40，结果夹在 0 到 255 之间。画在坐标上，就是一条整体上移 40 的直线，也就是图里那条蓝线。

后果是算术问题，不是审美问题：215 及以上的输入全部变成 255。220 的高光和 250 的高光最后都是 255，它们之间的差别永久消失。提亮后的天空变成一整块死白，原因就在这里。暗部反而完好，输入 10 变成 50，所以亮度一开始感觉「安全」，坏只坏在图像顶部。

截断点可以直接算：255 − 40 = 215。一般地，+b 会吃掉 255 − b 以上的所有值；−b 会把 b 以下全部压成纯黑。

对比度是绕 128 的旋转，两端一起坏

对比度用 new = factor × (old − 128) + 128，滑块值 c 决定 factor = 259(c + 255) / (255(259 − c))；滑块 +42 约为 factor 1.4，也就是下文采用的取值。轴心是 128，中灰原地不动；128 以上往上推，128 以下往下压。factor 取 1.4 时，这条线比恒等线更陡。

解两个不等式，两个损坏区就出来了：

  • 1.4(x − 128) + 128 ≤ 0，得 x ≤ 36.6，0–36 的输入被压成黑。
  • 1.4(x − 128) + 128 ≥ 255，得 x ≥ 218.7，219–255 被截成白。

算一下代价。对比度 1.4 在底部毁掉约 14% 的影调范围，顶部再毁 14%，而 128 一点没动。亮度 +40 只毁顶部 16%。这就是「为什么对比度一调高，高光就爆，亮度却没这么难受」的具体答案：对比度同时攻击两端，而且中间调看起来没有变化，等你发现时已经晚了。

实操规则很简单：小步加对比度，盯住最暗的 12 和最亮的 235。在色阶图上，1.4 会让这两块分别贴到 0 和 255，和相邻的灰块再也分不出来。这是看得见、可复查的失败，不是主观判断。

伽马是幂曲线，端点钉死

伽马在面板上叫「中间调」，实际算的是 255 × (x/255)^(1/γ)。γ = 1.4 时，指数约 0.714。它和亮度最大的区别是端点：0 还是 0，255 还是 255，只有中间被抬起来。

从表里看，输入 128 变成约 156，输入 224 变成约 233，不是 255。极值处没有信息被扔掉。

代价是中间调之间的关系被非线性改写。它不是「把图调亮一点」，而是重新分配中间调的疏密，这也是它看起来比亮度自然的原因。

顺序真的会改变结果

滑块在工具里是一次性算完的，但你导出、重新打开、再调一轮时，顺序就有意义了。拿一个值为 200 的像素举例。

  • 先对比度 1.4 再亮度 +40：1.4(200−128)+128 = 228.8，再加 40 得 268.8，夹到 255。
  • 先亮度 +40 再对比度 1.4：先得 240，再算 1.4(240−128)+128 = 284.8，夹到 255。

两个都会截断，但中间值不同。靠近轴心的值，最终结果也会不同：在 160 上，先对比后亮度是 172.8 + 40 = 212.8，先亮度后对比是 1.4(200−128)+128 = 228.8。同样两个操作，输出不一样。任何只写「先调对比度再调亮度」却不给公式的教程，都是在猜。

安全做法是：在原图上一次调完，只导出一次，不要把导出的文件再打开调第二轮。每打开一次，就多一次量化、多一次截断的机会。这和元数据是同一个道理：反复保存丢字段，反复过像素丢影调。

还有个现实限制要记住：编辑类工具的工作画布长边上限是 3000 像素，超出会等比缩小，并且只导出 PNG。想保留中间结果就存 PNG，中途不要转成有损格式。

饱和度 −100 不等于黑白按钮

饱和度先算 luma：0.299R + 0.587G + 0.114B。三个权重加起来是 1，绿色占比最大，因为眼睛对绿最敏感。在色阶图上取四块颜色：

黄圆250, 204, 21196.9

饱和度拉到 −100，就是把每个像素塌到它的 luma 上，得到一张按这套权重加权的灰度图。一键「黑白」是代码里的另一条分支（grayscale: true），可能直接用浏览器自带的转换。多数图上两者几乎一样，但它们不是同一个操作，在饱和色上灰值会有小差别。所以「两个黑白选项结果不同」不是 bug，是两套实现。面板提示「−100 时图像变成黑白」描述的是结果，不是声明它等于那个滤镜按钮。

逐通道的例子更直观。黄圆是 R=250、G=204、B=21，luma 196.9。亮度 +40 后三个通道变成 290、244、61，夹成 255、244、61——红通道丢 35 级，绿蓝没动。所以提亮后的黄会偏淡、偏绿，因为截断是按通道发生的，不是按像素。对比度 1.4 更狠：R 算得 298.8 贴到 255，G 是 234.4，B 算得 −21.8 压到 0。蓝通道归零、红通道贴顶，一次亮度操作顺手把饱和度拉爆了，这就是「加对比度想更有冲击力，颜色却变得不是自己想要」的机制。同一组通道走伽马 1/1.4，大约得到 252、233、58，两端都不截断。

色温、锐化与暗角

色温是通道偏置：正值往黄推，负值往蓝推。它不是白平衡测量，背后没有开尔文数值。已知光源造成的偏色要用真正的白平衡工具；只是给扁平图形加点暖意，这个滑块够用。

锐化用反锐化掩模：复制一份做模糊，取 original − blur 当作高频细节，乘上强度再加回去。面板给扫描件建议 30–60，因为扫描文字边缘强、噪声低，放大差值能提升可读性；再往上会把噪声一起放大，每条边都出现亮边或暗边。用一维边缘算一行：1×3 核 [1,2,1]/4，强度 0.45。

位置 3 的边缘像素从 160 升到 173.5，紧挨着的两个邻居掉到 93.2，这两处下陷就是光晕。强度加倍，光晕线性变大；模糊半径加倍，光晕变宽。扫描件值得付这个代价，因为文字边缘是真实的高频信号；弱光噪点照片不值得，因为噪声同样是高频，会被一模一样地放大。面板的 30–60 是针对前一种情况的折中，不是通用推荐。

暗角按到中心的距离压暗，是唯一带空间性的控件。把它套在色阶图上，边缘的灰块会变，正好说明同一个数值在不同位置不等于同一份输出。

复现这套实验不需要特殊条件：下载色阶图 PNG，打开调色页，只设亮度 +40，导出，采样最亮的灰块和表对照；重新载入原图，把对比度调到 1.4，检查 12 和 235 是不是双双贴边；再载入原图，只用伽马，确认端点还在 0 和 255；最后把第二步的结果导出后再调一次，和单次处理的中灰比较，差值就是顺序与量化的影响。想单独看重新编码的影响，换 JPEG 版本重跑一遍。

最后一招：把六块灰阶当量具用。调之前采样 12 / 45 / 90 / 140 / 190 / 235 并记下来，调完再采一次。12 和 235 同时塌到 0 和 255，说明两端都被截断，再怎么推滑块也救不回来；只有 140 动了而两端没动，是伽马形状的改动；六块同幅平移，是亮度。三次读数就能认出是哪个操作，不用看代码——拿到一份没有历史的导出文件时尤其有用。

常见问题

亮度和伽马有什么区别？
亮度给每个通道加一个常数，255 − b 以上的高光会被截断。伽马走幂曲线，0 和 255 两个端点固定不动，只抬起中间调，所以不会毁掉干净的黑白极值。
为什么一加对比度高光就爆？
对比度以 128 为轴心，算式是 factor × (x − 128) + 128。factor 取 1.4 时，219 以上的输入被截成白，37 以下的输入被压成黑。
饱和度 −100 和黑白滤镜是一回事吗？
不完全一样。饱和度按 0.299/0.587/0.114 的权重把像素塌到 luma 上；黑白滤镜是代码里另一条独立的灰度分支。多数图结果相近，饱和色上灰值会有差别。
扫描件锐化为什么建议 30–60？
反锐化掩模放大的是 original − blur。扫描文字的边缘强、噪声低，中等强度就能提升可读性；再高会把噪声一起放大，并在边缘留下亮边或暗边。
锐化该放在缩放之前还是之后？
之后，在最终的像素网格上做。先锐化再缩放，等于让缩放滤镜把你刚造出来的光晕重新插值一遍。
